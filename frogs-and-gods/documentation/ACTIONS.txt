# Frogs & Gods — Action Library Reference

> **For Claude agents**: This file is the canonical registry for the Action Library.
> When implementing a new action, follow the steps in "How to Add a New Action" below.
> Update BOTH the appropriate action table AND the ACTIONS.md when you make changes.

---

## The "Inhale-Exhale" Architecture

Actions in Frogs and Gods are processed in batched 500ms "sub-ticks". To prevent database deadlocks and ensure absolute chronological fairness based on initiative rolls, actions do **not** query or write to the database directly.

Instead, they operate on a `SimulatedState` object. 

1. **The Inhale:** The `tickProcessor` loads all relevant chunks, frogs, predators, and items into memory (`SimulatedState`).
2. **The Living Ledger:** Actions are sorted by initiative and passed the `SimulatedState` to validate and execute. Changes are pushed into an `UpdateInstruction[]` array and applied back to the `SimulatedState` immediately, so subsequent actions see the updated reality.
3. **The Exhale:** After all actions resolve, the `tickProcessor` writes all queued `UpdateInstruction`s to the database in a single atomic transaction.

**CRITICAL RULE:** An action handler file should **NEVER** import from `../db`. If you need to read the state of the world, read it from `state`. If you need to change the world, mutate it via `state.updateX()` and push to `out`.

## Action Contract

Every action file must export a single handler object (`ActionHandler`, `PredatorActionHandler`, or `GodActionHandler`) with three synchronous/memory-bound methods:

```typescript
import type { ActionHandler } from "./_types";

export const myActionHandler: ActionHandler = {
  // @param ctx.frog        - Pre-resolved Frog row (never null here)
  // @param ctx.payload     - Typed payload from the client message
  // @param state           - SimulatedState (In-memory DB replica)
  // @returns FUMBLE code to consume the turn; other failures return { ok: false }
  validate(ctx, state) { ... },

  // Only called when validate() returns { ok: true }
  // Must write changes to `state` and push an instruction to `out`
  execute(ctx, state, out) { 
    state.updateFrog(ctx.frog.id, { currentHp: 5 });
    out.push({ type: "FROG_UPDATE", id: ctx.frog.id, changes: { currentHp: 5 } });
    return { success: true, data: { ... } };
  },

  // Fire-and-forget: pushes to ephemeral action log and notifies the owning user via WS
  // Can be async or synchronous depending on action.
  broadcast(ctx, result, notify) { ... },
};
```

## Fumble Rules

A **Fumble** consumes the actor's turn for the entire 10-second heartbeat.

| Trigger                                   | Returns                        |
|-------------------------------------------|--------------------------------|
| Equip capacity exceeded (`equipCapacity`) | `{ ok: false, code: "FUMBLE" }` |
| Inventory capacity exceeded (`inventoryCapacity`) | `{ ok: false, code: "FUMBLE" }` |
| Storing a CONTAINER inside a CONTAINER    | `{ ok: false, code: "FUMBLE" }` |
| Item's `blockedActions` contains the action type | `{ ok: false, code: "FUMBLE" }` |

When `validate()` returns a FUMBLE code, the processor will insert a sentinel `resolved` pending_action into the DB, consuming the frog's slot.

**Non-fumble failures** (wrong range, item not found, wrong target) return `{ ok: false }` with no code and do NOT consume the turn.

## Utility Library (`_utils.ts`)

Instead of writing common spatial queries or damage calculations from scratch, use the shared utility library.

### 1. Item-Based Fumble Check (Required in Every Action)

Every `validate()` must call `checkItemFumble()`:

```typescript
import { checkItemFumble } from "./_utils";

// Inside validate():
const fumble = checkItemFumble(ctx.frog!.id, "MY_ACTION", state);
if (fumble) return fumble;
```

### 2. Spatial Queries

```typescript
import { getEntitiesAt } from "./_utils";

// Inside execute():
const { frogs, predators } = getEntitiesAt(state, targetX, targetY);
```

### 3. Combat & Damage

Use `applyDamage()` to handle HP reduction. It automatically updates the `SimulatedState` and pushes the `FROG_UPDATE` or `PREDATOR_UPDATE` instruction to the queue.

```typescript
import { applyDamage } from "./_utils";

// Inside execute():
applyDamage(state, out, "PREDATOR", predatorId, 7);
```

## How to Add a New Action

1. **Create the file** at `server/actions/<action_name_lowercase>.ts`
2. **Export a named handler** that satisfies `ActionHandler` from `./_types.ts`
3. **Write Logic against SimulatedState** (do NOT import the db)
4. **Register it** in `server/actions/index.ts` → `ACTION_REGISTRY`
5. **Add a Zod input schema** in `shared/game.schema.ts`
6. **Update this file**: add a row to "All Actions", remove it from "Upcoming Actions" if it was listed.
