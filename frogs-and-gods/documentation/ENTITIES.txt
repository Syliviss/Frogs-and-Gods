# Frogs & Gods — Entity Library Reference

> **For Claude agents**: This file documents the Entity Library: the AI-driven predator
> system, how it wires into the heartbeat engine, and the DB schema for each entity type.
> When adding a new entity type, follow "How to Add a New Entity" at the bottom.

---

## 1. Overview

The Entity Library lives in `server/entities/`. It is a **decoupled AI registry** that runs
separately from both the God action pass and the Frog DEX-sorted pass.

**Why it exists:**
- Frogs and Gods are player-controlled — their actions are queued by WebSocket messages.
- Predators are AI-controlled — their actions are calculated by the server at the start of
  each heartbeat cycle and queued as `pending_actions` with future `resolveBucket` values.
- Keeping entity logic in `server/entities/` prevents coupling predator AI to the frog or
  god action systems, and allows new entity types to be added without touching existing code.

**Key invariant:** Every entity action goes through `pending_actions`. No direct DB writes
happen from the AI brain — all state changes flow through the same action validation and
execution pipeline as frog actions.

---

## 2. Architecture

```
heartbeat.ts
  └── emit("cycle_start")             ← fires at Tick 0 of each new 10s cycle

socket.ts (listener)
  └── processEntityIntents(notify)    ← server/entities/index.ts

server/entities/index.ts              ← REGISTRY
  ├── getActivePredators()
  └── route by enemyType:
       └── "SNAKE" → calculateSnakeIntent(predator)   ← server/entities/snake.ts

server/entities/snake.ts              ← SNAKE AI BRAIN
  └── queues SLITHER or STRIKE pending_action with future resolveBucket

tickProcessor.ts (on every subtick)
  ├── Pass 1: processGodActions()
  ├── Pass 2: processPredatorActions()   ← resolves SLITHER / STRIKE / WRAP
  └── Pass 3: DEX-sorted frog pass
```

### Flow summary

1. A 10-second heartbeat cycle ends.
2. `heartbeat.ts` emits `"broadcast"` → `purgeResolvedActions()` runs, `ENGINE_TICK` is sent to clients.
3. `heartbeat.ts` restarts its subtick timer, enters `lock_in` phase, then emits **`"cycle_start"`**.
4. `processEntityIntents()` fires: each active predator's AI brain calculates its intent for this cycle.
5. Each intent becomes a `pending_action` row with a `resolveBucket` set in the future.
6. Every 500ms, `processAllActions()` runs. When a predator's `resolveBucket` arrives, `processPredatorActions()` resolves the action.

## 3. Heartbeat Wiring

### `cycle_start` event — `server/engine/heartbeat.ts`

```typescript
private _runMainTick(): void {
  this.phase = "broadcast";
  this.emit("broadcast");           // ← 10s tick: ENGINE_TICK to clients, purge old actions
  this._clearTimers();
  this.phase = "lock_in";
  this._startTimers();              // ← new subtick interval + 10s timeout begin
  this.emit("cycle_start");         // ← Tick 0: entity AI queues intents
}
```

### Listener — `server/websockets/socket.ts`

```typescript
heartbeat.on("cycle_start", () => {
  void processEntityIntents(emitToUser);
});
```

`processEntityIntents` is non-blocking (fire-and-forget). If the DB is slow or no predators
exist, the cycle proceeds normally.

## 4. Sub-Tick Initiative Math

All entity actions are delayed by an **initiative formula** calculated at Tick 0:

```
Action Tick = ((10 - speed) * 2) + d4_roll
resolveBucket = currentBucket + Action Tick
```

Where:
- `speed` = `predator.statsJson.speed` (integer 1–10; default 5 if unset)
- `d4_roll` = random integer 1–4 (`Math.ceil(Math.random() * 4)`)
- `currentBucket` = `Math.floor(Date.now() / 500)` at intent-calculation time

### Initiative table

| Speed | Formula range   | Delay sub-ticks | Wall-time         | Notes                        |
|-------|-----------------|-----------------|-------------------|------------------------------|
| 10    | (0*2) + 1–4     | 1–4             | 0.5–2 s           | Lightning-fast predator      |
| 8     | (2*2) + 1–4     | 5–8             | 2.5–4 s           | Quick                        |
| 5     | (5*2) + 1–4     | 11–14           | 5.5–7 s           | Average (default)            |
| 3     | (7*2) + 1–4     | 15–18           | 7.5–9 s           | Sluggish                     |
| 1     | (9*2) + 1–4     | 19–22           | 9.5–11 s          | May spill into next heartbeat |

**Spillover:** A speed-1 snake with d4=4 gets `resolveBucket = currentBucket + 22`. Since a heartbeat
is 20 sub-ticks (10s / 500ms), this action resolves during the next heartbeat cycle. The snake will
appear to skip a turn from the player's perspective. This is intentional — extremely slow entities
have an inherent chance of failing to act within a cycle.

**d4 variance:** The 1–4 roll adds jitter so entities with the same speed don't always resolve on the
same frame. Two speed-5 snakes in the same chunk will resolve at slightly different times.

## 5. Snake AI — State Machine

**File:** `server/entities/snake.ts`
**Export:** `calculateSnakeIntent(predator: Predator): Promise<void>`

### States

```
┌──────────────────────────────────────────┐
│             calculateSnakeIntent()       │
│                                          │
│  statsJson.wrapping != null?             │
│    YES → HOLD (return; frog must act)    │
│    NO  ↓                                 │
│                                          │
│  currentHeartbeat - lastMealTick > 18?   │
│    NO  → IDLE (return; satiated)         │
│    YES ↓                                 │
│                                          │
│  frogs in chunk?                         │
│    NO  → IDLE (no prey; return)          │
│    YES ↓                                 │
│                                          │
│  closest frog Chebyshev dist <= 1?       │
│    YES → queue STRIKE                    │
│    NO  → queue SLITHER toward frog       │
└──────────────────────────────────────────┘
```

### Hunger mechanics

- **Storage column:** `predators.lastMealTick` — integer, stores the **heartbeat number** at which the
  snake last ate. Heartbeat number = `Math.floor(Date.now() / 10_000)`.
- **Hungry threshold:** `currentHeartbeat - lastMealTick > 18` (18 heartbeats × 10s = 3 minutes).
- **Hunger reset:** Only when a frog **dies** from a STRIKE (newHp ≤ 0). A snake that wraps but
  whose target escapes does NOT reset hunger. Hunger is reset inside `strike.ts` execute:
  `updatePredator(id, { lastMealTick: Math.floor(Date.now() / 10_000) })`.
- **Default:** `lastMealTick = 0` on spawn. `currentHeartbeat` in 2026 is ~174M → snake is
  immediately hungry when spawned (174M - 0 >> 18). This is intentional: newly spawned snakes hunt.

### Frog detection

The snake searches for frogs within its own 16×16 chunk using the spatial bounds:
```
minGX = chunkX * 16,  maxGX = minGX + 15
minGY = chunkY * 16,  maxGY = minGY + 15
getFrogsInBounds(minGX, maxGX, minGY, maxGY)
```
Dead frogs are filtered out (`!frog.isDead`). The snake targets the closest survivor by Chebyshev
distance. If multiple frogs are equidistant, the first one returned by the DB query wins (arbitrary,
no tiebreak needed).

### Slither pathfinding

The snake moves one Chebyshev step toward the closest frog each cycle:
```
targetGridX = predator.gridX + Math.sign(closestFrog.gridX - predator.gridX)
targetGridY = predator.gridY + Math.sign(closestFrog.gridY - predator.gridY)
```
This is naive greedy movement — one step per heartbeat, diagonal allowed. No pathfinding around
obstacles. Future: replace with A* or flow-field if obstacle avoidance is needed.

## 6. SNAKE DB Schema

### `predators` table columns (relevant to SNAKE)

| Column        | Type         | Default | Notes                                                        |
|---------------|--------------|---------|--------------------------------------------------------------|
| `id`          | serial PK    | —       | Predator's DB identity; used as `actorId` in pending_actions |
| `enemy_type`  | enum         | —       | Must be `"SNAKE"` to route to snake.ts                       |
| `ai_type`     | enum         | —       | `"HUNTER"` for active snakes; `"DOCILE"` for passive future use |
| `grid_x`      | integer      | —       | **Head** position — authoritative tile X                     |
| `grid_y`      | integer      | —       | **Head** position — authoritative tile Y                     |
| `chunk_x`     | integer      | —       | `Math.floor(grid_x / 16)` — denormalized for chunk queries   |
| `chunk_y`     | integer      | —       | `Math.floor(grid_y / 16)`                                    |
| `current_hp`  | integer      | —       | Hit points; set to 0 when killed                             |
| `last_meal_tick` | integer   | 0       | Heartbeat number of last kill. 0 = never fed (always hungry) |
| `stats_json`  | jsonb        | null    | See PredatorStats below                                      |

### `statsJson` shape for SNAKE (`PredatorStats`)

```typescript
interface PredatorStats {
  // SNAKE-specific fields:
  speed?:    number;                           // 1–10; default 5 if unset
  segments?: Array<{ x: number; y: number }>; // Body tiles. segments[0]=body1, [1]=tail
  wrapping?: { targetFrogId: number } | null; // Active constriction target
  // Inherited flexible fields:
  path?:     number[][];                       // Reserved for future pathfinding
  mutations?: string[];                        // Future mutation flags
  [key: string]:  unknown;
}
```

### Segment layout

```
SNAKE body: [HEAD] → [segments[0]] → [segments[1]]
             ↑                              ↑
       predators.gridX/gridY         tail (dropped on SLITHER)
```

On spawn, initialize segments so the snake starts coiled or in a line:
```typescript
statsJson: {
  speed: 5,
  segments: [
    { x: spawnX, y: spawnY },      // body1 = same as head (coiled)
    { x: spawnX, y: spawnY },      // body2 = same as head (coiled)
  ],
  wrapping: null,
}
```
The body will spread out naturally as the snake slithers.

### `frog.statsJson.wrappedBy` (companion field)

When a frog is being constricted, `wrappedBy` is set on the frog side:

```typescript
// FrogStats addition:
wrappedBy?: number | null;  // predator.id of the snake holding this frog
```

Both fields (`predator.statsJson.wrapping` and `frog.statsJson.wrappedBy`) must be cleared
together. This is handled atomically by `rollConditionCheck()` in `_conditionUtils.ts` on escape,
or by death cleanup in the relevant action.

## 7. Condition System (Entity-Driven)

**File:** `server/actions/_conditionUtils.ts`

Predator actions can impose conditions on frogs that affect future frog action resolution. The
condition check is embedded in each affected frog action's `validate()` phase via a single utility
call. This avoids any passive sweep — conditions are evaluated on-demand when the frog tries to act.

### WRAP condition

Set by: `strike.ts` execute (optimistically) + `wrap.ts` execute (canonical).
Cleared by: `rollConditionCheck()` on successful escape, or death of either entity.

**Escape roll:** `Math.max(frog.statsJson.str, frog.statsJson.dex) >= 15`

A frog with str < 15 AND dex < 15 **cannot** escape without stat growth or divine intervention. A
frog with either stat ≥ 15 always escapes on their next action attempt.

**Turn cost:** A failed escape roll returns FUMBLE — the frog's turn is consumed struggling. The
snake can continue hunting other frogs or hold the wrap for the rest of the cycle.

### Adding a new condition

1. Add a flag to `FrogStats` in `drizzle/schema.ts` (e.g. `stunned?: boolean`).
2. Add a block in `rollConditionCheck()` in `_conditionUtils.ts` that checks and clears the flag.
3. Have the entity action that imposes the condition set the flag during `execute()`.
4. Any frog action that should be blocked or modified by the condition will automatically
   pick it up via the `rollConditionCheck()` call in `_moveHelper.ts` (movement) or the
   individual action's `validate()`.

## 8. Admin Spawn / Kill Flow

Predators can be created and destroyed via the Enemy Management tab in the Admin panel, without waiting for game events or AI triggers.

**Spawn flow:**
1. Admin fills in X/Y, type, AI, speed, HP → clicks "Spawn Enemy"
2. tRPC `admin.triggerSpawn` mutation queues a `SPAWN_PREDATOR` action in `pending_actions` (actorId = 0, current 500ms bucket)
3. On the next heartbeat, `processGodActions()` picks it up → `spawnPredatorHandler.validate()` checks chunk exists and tile is not `≈` → `spawnPredatorHandler.execute()` inserts the predator row
4. The Enemies tab auto-refreshes every 10 seconds; the new row appears

**Kill flow:**
1. Admin clicks "Smite" on any row
2. tRPC `admin.triggerKill` mutation queues a `KILL_PREDATOR` action (actorId = 0)
3. On the next heartbeat → `killPredatorHandler.execute()` hard-deletes the predator row
4. The predator's `'S'` glyph disappears from the canvas on the next vision refetch

**Key files:**
- `server/actions/spawn.ts` — SPAWN_PREDATOR handler
- `server/actions/kill_predator.ts` — KILL_PREDATOR handler
- `server/routers/admin.ts` → `getEnemies`, `triggerSpawn`, `triggerKill`
- `client/src/components/admin/EnemiesTab.tsx` — UI

## 9. How to Add a New Entity Type

1. **Create** `server/entities/<type>.ts` with:
   ```typescript
   export async function calculate<Type>Intent(predator: Predator): Promise<void>
   ```
2. **Add action types** to `server/actions/_predator_action_types.ts`.
3. **Create action files** in `server/actions/` implementing `PredatorActionHandler`.
4. **Register actions** in the `PREDATOR_ACTION_REGISTRY` in `server/actions/index.ts`.
5. **Add a routing branch** in `server/entities/index.ts`:
   ```typescript
   if (predator.enemyType === "FLY") {
     await calculateFlyIntent(predator);
   }
   ```
6. **Document** in this file (ENTITIES.txt) and in ACTIONS.txt.
